# Receptionist, Senior Therapist and Doctor release-readiness audit

Audit started **2026-11-04** and completed **2026-11-05, Africa/Cairo**. Scope: the existing Angular application, .NET API, persisted handoffs, and readiness to begin CEO work. This is an audit; application fixes and CEO implementation were not made.

**Decision: NOT READY.** The main downstream clinical and financial workflows work in isolation, but normal patient registration is broken, legacy Senior endpoints permit unauthorized changes to signed clinical records and plans, an unsigned assessment can disappear from the actionable task list after Reception checkout, and appointment date filtering is inconsistent with the clinic calendar. These findings are reproduced below. Passing previous reports and the current backend suite do not override these failures.

## 2. Roles, screens and responsibilities

The username `SuperAdmin` is verified through its actual backend `Admin` membership. Frontend `roleGuard` also accepts `Admin` and `SuperAdmin`; backend supervisory roles are `Ceo`, `Admin`, `Owner`. A username or frontend role alias alone does not grant an API permission.

Reception operations normally require `Receptionist,Ceo,Admin,Owner`. Clinical ownership rules apply in the new appointment/reassessment workflows, with supervisory exceptions. The legacy Senior authorization failure in F2 is an exception to the intended assignment boundary and must be included in any description of actual permissions.

## 3. Patient journeys and actual persisted results

### A. Self-pay, session by session

2. In E1, a valid API registration supplied the username and created patient 3. Reception booked a paid initial assessment for **EGP 100**, initially unpaid. Arrival was rejected until a real EGP 100 patient receipt was collected.
3. Reception recorded arrival. Assigned Senior saved diagnosis, mobility instructions, **3 prescribed sessions**, **2 per week**, and assigned Doctor. Another Senior's attempt at this new completion endpoint returned 403. Repeating the same signoff did not create another plan. Reception then checked out the assessment.
4. Reception booked one `PerSession` treatment for EGP 100 against plan 3. Doctor start before arrival returned 409; Reception arrival with zero patient coverage also returned 409. One EGP 100 collection, retried with the same key, created one receipt. Arrival then succeeded.
5. The Doctor saw `Arrived` with no treatment start time. Reception checkout before clinical end returned 409. Assigned Doctor started, saved notes, and ended. Repeated End left **one** completed session. After clinical end the state was `TreatmentFinished` and departure remained null.
6. Reception checked out; repeating checkout did not change timestamps/progress. Doctor readback showed `Departed`, plan completed count **1**, saved final notes and all four distinct lifecycle timestamps. Appointment 2, session 1 and invoice 2 retained their links.

The browser repeated the downstream sequence with a Free initial assessment, then a treatment priced **EGP 100**, **EGP 20** paid at booking and an **EGP 80** shortfall. ## 4. Handoff rules and state interpretation

| Stage | Appointment / clinical state | Persisted evidence | Who acts next |
| --- | --- | --- | --- |
| Booking | `Pending` / `Scheduled` | Planned start/end, assignment, room, session/plan link; invoice/agreement; optional actual deposit | Reception collects/checks in |
| Reception arrival | Appointment `InProgress` (UI **In Progress**), workspace `Arrived`; linked treatment session still `Pending` | `ActualCheckIn`, session `CheckIn` | Assigned Doctor / covering Senior starts |
| Actual treatment | Workspace `Treating`; session `InProgress` | `TreatmentStartedAt/By`, versioned clinical draft | Treating clinician saves and ends |
| Clinical completion | Workspace `TreatmentFinished`; session `Completed`; appointment still `InProgress` | `TreatmentEndedAt/By`, finalized record, plan completed count, invoice `DeliveredAt` | Reception records departure |
| Reception departure | Appointment `Completed`, workspace `Departed` | `ActualCheckOut`, session `CheckOut` | Room and patient occupancy released |

Status values also include appointment `Cancelled`, `NoShow`, and workspace `LegacyCompleted`. Legacy completion must not be treated as proof of an actual start/end/departure timestamp. Plan status remains `Active`/`Inactive`; delivering all prescribed sessions does not imply a new invented discharge transition. Invoice values are `Pending`, `Paid`, `Cancelled`, `Waived`; payment values include `Pending`, `Paid`, `PackageCovered`. A payment gate can be satisfied while an insured invoice remains Pending because the insurer has not settled.

Clinical completion is counted once by session identity, not by clicks, receipts, appointment count or Reception departure. The main audit retried End, assessment completion, payment and checkout with unchanged intent; records remained stable. Current HTTP tests also exercise simultaneous starts/claims/bookings. Assignment changes preserve appointment/plan/session and financial links; review completion changes clinical review records, not attendance or money.
